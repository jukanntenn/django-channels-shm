# DCS-RFC: 每环 flush 代数栅栏

Status: implemented

[English](2026-09-04-flush-generation-fence.md) | 中文

## Problem

`flush()` 在全局 flock 下重置环计数器、槽位状态与 slab 池，但 send/receive 热路径从不取该锁。与 flush 并发运行的 `send` 或 pump `drain` 与重置写入交错，其交错后果不只是"丢消息"：在重置前取票的生产者会在重置后发布过期的 `seq`（把槽位卡死到 compaction 到来）；最坏情况下，生产者迟到的 `overflow_off` 写入会把指针复活到已被 `slab.reset` 清空的池中，消费者读到的是回收页或垃圾字节（内容损坏），而消费者迟到的 `slab.free` 会把过期页推回全新的 free list 造成二次分配。docstring 里"必须在静止态调用"是跨进程无法强制的调用者纪律，而规范自身的 flush 语义决定了测试与管理工具会例行调用它。

## Decision

每个环携带一个 **flush 代数计数器**，两条热路径在各自临界区前后校验它：

- **布局 v2**（`layout.rs`）：`RING_GENERATION`（u64，release 序）位于环头偏移 40；`RING_HEADER_SIZE` 为 48。`VERSION` 为 2，且 `check_magic` 折入版本校验——旧布局写的区域检查失败，走首进程重建路径（重新初始化），而不是按新槽步长错读。
- **reset**（flush 路径，持锁）在动计数器、槽位与池**之前**以 release 序升代数。
- **enqueue** 在认领前读 `g0`；载荷写完后重读。变化 → 对未发布轮次**零写入收回**：只 CAS 清掉自己的 owner 记录（`self → 0`）——对从未发布的轮次，reset 状态本身就是正确的终态，而此处任何 seq/溢出写入都可能砸掉 flush 后在同一槽位、以同一票号重新认领的新轮次（跨代票号别名——首轮票在 reset 后重新可认领）。未变 → 发布 `seq = pos + 1`、清 owner 后再读一次；变化 → 用一次 CAS 把已发布轮次收回为墓碑值 `pos + cap`（仅丢消息；别名窗口见 Consequences），已认领的消费者仍在完好载荷上完成，其溢出释放由声明 CAS 保证恰好一次。
- **dequeue** 在每次读 `dequeue_pos` 旁采样代数；认领成功后代数变化即证明池已被清空——它把已认领槽位回收为墓碑，**不**把溢出页释放进全新 free list，返回 `None`（调用者从全新 `dequeue_pos` 重试）。
- **dequeue** 在竞争认领上同样只写墓碑 CAS 与 owner 清理；被认领轮次的溢出页绝不释放进全新池（代数变化即证明池已被重置——在那里释放正是二次分配隐患）。该编码下不可再缩的是跨代票号别名：reset 后新流量合法地重新认领相同票号，旧代生产者无法仅凭槽位值区分自己的轮次与新轮次。设计因此把竞争操作的写入压到最少（未发布轮次仅 owner-CAS；已发布轮次一次受控 CAS），并在 Consequences 中文档化两个幸存窗口。

## Alternatives considered

**等待静止的 flush（持锁扫描槽 owner，循环至干净）。** 败在：claim→owner 写入窗口只有 2–3 条指令且扫描不可见，竞争者的迟到 `seq` 发布仍会卡死槽位、迟到的 `overflow_off` 写入仍会复活已释放的页。

**逻辑 flush（把计数器与槽 seq 前推到各自下一张票；绝不回拨）。** 败在：竞争者的迟到发布会把已修复的槽回拨到前沿之后（卡死），溢出页问题原样保留——没有代数，竞争者无从得知自己的页已被释放。

**生产者侧基于共享 flush-pending 标志的 flock 门控。** 败在：标志本身也是新的共享状态（同样的布局代价），却用两次 flock 串行化本可用一次计数器检查解决的问题。

**仅文档化（把静止态纪律维持为契约）。** 作为最终状态败在：任何看似正确的调用者在仍有活跃 sender 时 flush 一层即可触达该损坏，而"纪律"不是内存序论证。它作为本方案落地前的临时缓解保留。

## Consequences

无界的 flush 临界区竞争就此关闭：竞争中的操作选择收回，而不是向被清空的池发布或从中释放页；最后一次代数检查与 `seq` 写入 / `slab.free` 之间的指令级窗口仍在，pump 的 P-01 坏消息容忍仍是最后防线。跨代票号别名另留两个窗口，均需生产者被 SIGSTOP 级病理跨 flush 停车：(1) 停在发布与发布后检查之间的生产者，其收回 CAS 可能命中复用同票号的新轮次——已被 accept 的 send **丢失**、绝不损坏（若跳过收回，flush 前的陈旧消息会带指向已清空池的指针浮出——内容损坏，严格更糟）；(2) 停车生产者自己迟到的载荷写入可能撕裂重新认领轮次的字节——撕裂字节在 pump 处过不了 msgpack 解包而被丢弃（P-01），不会作为应用消息投递。专门的别名压力测试（停车的 2 MiB 生产者 + reset + 同槽新轮次）钉住收回不变式——已发布的新轮次绝不被墓碑化——并已验证对修复前的收回行为确定性失败（旧收回会把新轮次墓碑化）。Rust（生产者 + reset 风暴线程）与 Python（asyncio send/flush 交错）压力测试钉住更广的契约——不挂起、不崩溃、幸存消息可解析、风暴过后环与 layer 完全可用——版本门测试钉住 v1 区域重建。同一区域上新旧进程混跑在第一个新进程重建之前会互相损坏；在扩展的单机、单部署形态下可接受。实测代价（criterion，本机）：无竞争入队 36.8 → 40.6 ns，其中 CAS-claim 准入 +0.6 ns（36.8 → 37.4）、栅栏的 load + 分支 +3.2 ns（37.4 → 40.6）；出队 78.6 → 76.8 ns——均远在 100 ns 锚点门内，锚点通过。本机竞争数字运行间方差很大（同代码 8 线程入队两次运行分别 +58% 与 +2.5%）——单次竞争读数视为噪声；带锚点的无竞争门才是可靠信号。既有 flush 测试原样通过。
