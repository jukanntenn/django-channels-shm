# DCS-RFC: Ring protocol hardening — CAS-claim admission, idempotent repair, watchdog compaction

Status: implemented

English | [中文](2026-09-04-ring-protocol-hardening.zh.md)

## Problem

External review of the [Vyukov ring](./2026-08-02-lock-free-ring-slab-over-broker.md) found a family of correctness defects, most rooted in one design choice: enqueue took its ticket with `fetch_add` before inspecting the slot, so every `Full` return consumed a ticket with no seq accounting. A burnt ticket left a slot whose seq could never catch up to the ticket stream; the consumer stalled on it (head-of-line block), and one `ChannelFull` — amplified 4× by the layer's send retries — could permanently kill a ring that was physically empty. Around it: `pid_dead(u32::MAX)` returned true (`kill(-1,0)` broadcasts and "succeeds"; `/proc/4294967295` is missing → conservative-dead), so a slot parked in the `SLOT_RECOVERING` repair state was "recovered" again, degrading recover's CAS mutex to the no-op `RECOVERING→RECOVERING` and admitting a second repairer — a deterministic overflow double-free. Compact's `≥2×cap` advancement gate was fed by the very ticket-burning it repaired, and its `max(enq,deq)−cap` bound matched live unconsumed messages once burnt tickets inflated `enq`. The `seq>pos` enqueue branch span unbounded (whole-process freeze: pyo3 holds the GIL). The Python validator allowed 200-byte names against 128-byte in-shm fields (silent ring truncation misrouted messages; `channel_index_create` wrote past the field into the next slot). `capacity=0` panicked the ring (`pos % 0`) while `capacity or default` silently swapped it for the default. One more defect surfaced while fixing these: capacity=1 was never representable at all — `published-unconsumed` and `recycled-empty` both equal `pos+1`, so a second enqueue silently overwrote a live message with no `Full` signal.

## Decision

Enqueue admission is verify-then-claim (Vyukov CAS-claim): the ticket is consumed only after the target slot is verified EMPTY (`seq == pos`); every `Full` return happens before the claim, so `enqueue_pos` never advances on failure and a drained ring accepts the retried send on the same ticket. Owner tracking moved after the claim — the record now always describes a ticket this producer owns. The `seq>pos` branch (reachable only via a compact repair racing an in-flight producer) spins bounded — 64 yields, then `Full`. Slab exhaustion leaves a SKIP tombstone (`seq = pos + cap`) instead of a dead slot; the consumer's existing skip branch consumes it with zero new code.

The repair machinery is idempotent. Overflow pages are released claim-then-free everywhere (consumer read path, expiry path, recover, compact): a CAS on `SLOT_OVERFLOW_OFF` wins the right to `slab.free`, so a crash after the claim leaks a page (safe) where the old free-then-zero order double-freed it (free-list corruption). `recover_slot`'s seq store is a CAS from the observed value — it can never move a slot a concurrent repair or producer already advanced — and ownership clears only from `RECOVERING`. `pid_dead` rejects pids whose i32 view is ≤ 0, so the sentinel can never be "confirmed dead"; enqueue and dequeue treat a parked `RECOVERING` slot as busy (`Full`/`None`).

Compact lost its `≥2×cap` advancement gate: burnt tickets used to feed it, a stalled ring advances nothing, and the gate starved exactly the rings needing repair. Two-pass confirmation is now separated by caller cadence instead. `SLOT_RECOVERING` counts as ownerless — compact finishes a repair whose recoverer crashed, at the interrupted round's own ticket (`ticket+cap`); ownerless E1 residuals repair to the next targeting ticket (the fixed p-formula, regression-tested). The pump watchdog runs native `compact` under the global flock every tick, so E1/D1 residuals and crashed repairs self-heal within about two ticks.

Configuration edges fail fast: capacity < 2 is rejected by the layer (`ConfigurationError`), the manager, and the ring bindings (`ValueError`) — 0 divides by zero, 1 is not representable. Names are bounded to 128 by the validator and rejected with `ValueError` at every binding that copies a name into a fixed 128-byte field (channel/group index create, member add, ring enqueue).

## Alternatives considered

**Admission-by-counter, then wait for the slot (the fuller protocol proposed by one reviewer).** A producer that passes the counter admission and claims a ticket MUST then publish or tombstone — returning `Full` would burn the ticket — so it waits for a live previous-round consumer mid-copy, cross-process, while pyo3 holds the GIL; SIGSTOP, cgroup freeze, or plain scheduler starvation turns that into a whole-process freeze on a scheduling-reachable path (the same failure mode as the unbounded spin, wider trigger). It also required a consumer-side owner write-order change trading "claim-crash loses nothing" for "claim-crash drops one message". It lost to CAS-claim, which has no post-claim waiting at all: the near-full recycle window returns a transient, correct `Full` retried by the Python layer with proper `await` scheduling.

**Wire compact into the watchdog without changing the protocol (the minimal option).** It lost on its own evidence: burnt tickets both inflated compact's bound (deleting live messages on a schedule) and fed its advancement gate; wiring the watchdog alone would have made periodic compaction actively dangerous, and after de-burning, the gate would starve frozen rings forever.

**A one-line guard treating `RECOVERING` as a live owner.** It lost: a recoverer that crashed mid-repair parks the slot with its identity erased, and every observer would wait on it forever (compact skips owner ≠ 0); the idempotent body plus compact takeover is what makes the guard safe.

**Keep capacity=1 with a capacity-specific alias fix.** It lost: for a single-slot ring every future seq value is the consumer's READY marker for some reachable position — the consumer's skip chase always lands on a phantom read; the encoding cannot be repaired in-protocol, so rejecting it is the honest fix.

## Consequences

`ChannelFull` is transient again: a drained ring accepts the next send on the same ticket, FIFO and at-most-once hold under the full suite (fast, slow cross-process, recovery tiers), and a live message can no longer satisfy compact's repair condition (honest counters keep `enq − deq ≤ cap`). The E1 crash window (claim → owner store, ~3 instructions) now freezes its ring — enqueue `Full` at the wrap, receive empty — until watchdog compaction repairs it within about two ticks; freeze-then-heal, not cap−1 degradation, is the documented expectation the tests encode. A crash between the overflow claim and the free can leak one slab page (bounded, safe) — never a double-free. Configurations that previously corrupted silently now fail loudly: capacity 0/1 raise at construction, 129–200-byte names raise `TypeError`/`ValueError` at validation and at the bindings. The hot path swapped `fetch_add` for load+CAS (same RMW count, one extra load). Measured against the pre-fix tree (criterion, this machine): uncontended enqueue 36.8 → 40.6 ns and dequeue 78.6 → 76.8 ns including the [flush-generation fence](./2026-09-04-flush-generation-fence.md) — both far inside the 100 ns anchor gate; contended suites show no regression beyond run-to-run noise; every `bench/py` anchor passes. The existing suites pass unchanged except two mechanical adaptations where tests encoded the removed mechanism itself: the compact p-formula regression now injects the residual state directly instead of manufacturing it via burnt tickets, and the recover-CAS herd test moved from cap=1 (now unrepresentable) to cap=2; the recover test's assertions are untouched, while the compact test's burnt-ticket position assertions were restated as the no-burn invariant (same intent — the p-formula and hang-freedom). Twenty Rust and thirty-four Python regression tests pin the new invariants; coverage is 98.99% Rust (`cargo llvm-cov`, the pyo3 macro file excluded per its documented instrumentation limit) and 97% Python.
